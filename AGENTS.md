## The rule most often missed

**Every ASL rule lives in the Rules project alone** (`src/ASL/LimboDancer.Domains.Asl.Rules`). A rule is a calculator there that takes facts and returns a verdict. Play reads the state and the map, hands the facts over, and writes the events; it decides no rule. The Units projector asks the same calculators and applies their answers. Rules references Abstractions only, never Units, Maps, or Play. Any new project (for example `ASL.Turns`) is bound the same way: it gathers facts and presents verdicts; it does not decide legality, eligibility, timing, outcomes, or thresholds itself.

A sign that a rule has been written in the wrong place: code outside Rules that cites a rule number (A1.31, C9.3, G10.11) while computing the decision itself.

**One rule, one calculator.** A rule is decided by one calculator. Where two decide it today (C9.3 has `ScenarioA1AreaCalculator` and the `TurnSpotter*Rules`), the claim that takes the rule makes them one.

### Step 1: claim

- **The claim commit.** A claim is a numbered rule section, or a subsection group where the section is large (the plan's question 1). On an up-to-date `main`, in one commit that changes the inventory and the status lines and nothing else: add the claim's row to the claims table (its id, you as Agent, the other agent as Reviewer, the branch you will work on, the Rules files you will change, state "claimed", the date), and set each of its rows' Owner cell to "claim (agent)", for example "C9.3 (Codex)", and its Claim state to "claimed". Run `python code-builders/documents/pass_rules_status.py`, which rewrites the status lines of the passes the claim's rows belong to, and `python code-builders/documents/claim_check.py`; then push to `main` (an edit to an existing document goes straight to main). The push is the lock: if it is rejected as not a fast-forward, fetch, read the table, and take another claim if yours is taken.
- **Its ASOP rows.** The ASOP's rows (Appendix 2) are steps of the sequence, not rules. The claim commit takes every ASOP row whose step cites only the claim's own rules; `python code-builders/documents/asop_steps.py <rule>...` lists the steps that cite them and what else each cites. A step that also cites other sections' rules (2.22A cites C9.3 and the whole of Prep Fire) is a step of its phase: it stays open until track 3 accepts that phase. A contract's Place still names the step it applies at.
- **Its held files.** While a claim is claimed or built it holds the Rules files it lists: no other claim may list them, and a branch may change a file of the Rules project only when a claim of that branch lists it. A file that turns out to be needed is added to the claim by the same kind of commit first.
- **Shared holds.** A large file that many rules use (the ordnance calculator, its eligibility, its models) is listed as `Name.cs (shared)` when the claim changes it only at its edges: a call into the claim's own calculator, a field on a record. Several claims may hold a file shared at once; a claim that decides its rule inside the file holds it whole. The claim moves its rule's logic into its own calculator file rather than hold a shared one whole.
- **Files outside Rules are not held.** Play, Units, ASL.Turns, and MapStudio files are shared by every claim's wiring. Before claiming, `python code-builders/documents/claim_check.py --touched` lists what every open claim's branch changes.

### Step 2: build

- **A claim builds the Rules library, not its callers** (the user, 2026-10-29). It changes the Rules project, its tests, its minigame bundle, and the Rule Workbench where the bundle needs it. Play, the Units projector, ASL.Turns, Maps, and the Studio's other pages are track 3's: the claim lists their sites that decide its rule in its wiring row (the last section below), and changes none of them. An old Rules member that callers use keeps its name and its answer (the Rules conventions, section 2, step 5), so a claim changes no recorded game's replay. `claim_check.py` warns when a claim's branch strays outside this scope.
- **On the claim's branch:** read every rule of the claim on its PDF page; map where the code decides it today with `python code-builders/documents/rule_sites.py <rules> --words <words>` and read each site; write the calculator under the [Rules conventions](src/ASL/LimboDancer.Domains.Asl.Rules/CONVENTIONS.md), section 2 (a claim on a rule already built is its audit, by the same steps) and its wiring contract; check its minigame position on the workbench; then its tests; then the rows, the coverage document, the backlog, `minigames_column.py` (the Minigames column, from the bundles' manifests), and `pass_rules_status.py`; then the state "built" in the table and the rows (the plan's section 4.3). The proving slice's design (`src/ASL/docs/Designs/ASL Rules-First Proving Slice Design.md`) shows the contract, the bundle, and the Rule Workbench at work.
- **A contract's owner facts.** A Unit fact disclosed to its Owner (or Opponent) names the unit fact whose side decides who may know it. When it names itself, the Rule Workbench lets each side pick only a unit of a side that may know it, and the other side the enemy's "?" stack, whose handle carries its side and no identity (the review of Wiring Prompt 001, PS4); when it names another fact, that fact must be known to the viewer first (disclosed to All, or gathered), or no side can ever fill the row.
- **Overlaps.** `python code-builders/documents/claim_check.py --base origin/main --branch <your branch>` warns when your branch changes a file outside Rules that another holding claim's branch changes too. Push your branch early so the other agent's check sees it, and agree who goes first when it warns.

### Step 3: merge main, then the pull request

- **Merge, never rebase** (no force push). Two claims edit the same documents (the inventory, the status lines, the coverage counts, the backlog, the time log) on different rows, and git calls neighbouring rows a conflict: `python code-builders/documents/settle_documents.py` settles those, rewrites the generated parts, renumbers a backlog section that collides, and leaves only true conflicts for you.
- **The check.** `python code-builders/documents/claim_check.py --base origin/main --branch <your branch>` must pass before a pull request. CI runs it on every pull request and every push, with the status-line check, and the merge gate's strict stage runs both.
- **No gate per rule claim; a batch gate every five** (the user, 2026-10-29; the plan's section 4.3). A rule claim that stays in its scope changes no game's replay, so it merges on its own unit tests and a green CI run, without the merge gate. After every fifth rule claim merged since the last batch gate (the inventory's section 6 records it, and `claim_check.py` counts the merges and holds the sixth), the agent that merged the fifth runs the gate on an up-to-date main: `bash code-builders/merge-gate/gate.sh rules-batch <last batch gate> baseline`, then `build`, `proofs`, and `carry`. No game may differ; a difference is a member whose answer a claim changed, fixed forward by a small pull request. Then record main's proved commit as the last batch gate, and write Codex's prompt for the wiring the batch opened with `python code-builders/documents/wiring_prompt.py [--note "..."]`: it adds the next numbered file in `src/ASL/docs/Prompts/Codex Wiring/`, written from the board (every open wiring row by capability, the batch's new rows marked, the wiring claims in progress, the rule claims waiting for review). The record and the prompt go to main in one commit. `carry` files the baseline under the new commit, so the next batch gate needs no base stage.

### Step 4: review

- **The agent that did not build the claim reviews it,** read-only: the rules against the PDF and what a side may know (question 3). When only one agent is working, a sub-agent reviews. The reviewer sets the state "reviewed".

### Wiring claims (track 3)

The plan's section 9.1. A rule claim builds a calculator and changes no caller; a wiring claim moves the callers onto it.

- **The wiring row.** When a rule claim reaches "built", it adds its row `W-<claim>` to the inventory's section 7: the sites outside Rules that decide its rule today, each with the calculator method that replaces it (from its design's map, the Rules conventions' section 2, step 1); the old Rules members to remove once their callers move; and the behavior changes the wiring will bring.
- **To claim.** A wiring claim takes the open rows of one capability (fire, movement, rout, rally, close combat, setup and work, the turn's boundaries) whose rule claims are built. On an up-to-date `main`, in one commit that changes the inventory and nothing else: add its row to section 8 (id `wire-<capability>`, numbered when a capability is wired in parts; you as Agent, the other agent as Reviewer, its branch, the files it will change by path under `src/ASL/`, whole or `(shared)`, its capability, state "claimed", the date), and set each of its wiring rows' Owner to "claim (agent)" and State to "claimed". Run `claim_check.py`, then push to `main`: the push is the lock, as for a rule claim.
- **To build.** On its branch, change only the files it holds, their tests, and the old Rules members its rows name for removal. Every caller gathers facts and asks the calculator; a page that filters a list asks the same `...Refusal` the command will. Behavior changes land here, so each wiring claim runs the merge gate of its own: name every replay or sweep difference as one of the rows' changes, and keep older recorded games on their recorded reading. Then merge main (step 3) and the state "wired" on the claim and its rows. When every wiring row of a rule claim is wired, set that rule claim and its inventory rows to "wired".
- **Review.** The other agent reviews it: each site now asks the calculator, and each behavior change matches the rule. The reviewer sets "reviewed". "Accepted" comes when track 3 accepts the phases the capability serves.

## Other rules that apply to every change

- **The rulebook first.** Read the rulebook PDF before stating or coding a rule, and cite the rule and its page. Search the whole rulebook before saying what a counter or rule needs.
- **How a change reaches main.** Code, project files, lock files, the workflows, anything under `code-builders`, and any commit that adds, removes, or renames a file go through a pull request and a green CI run. Only edits to the text of existing documents go straight to main, and one kind of new file: a Codex wiring prompt (`src/ASL/docs/Prompts/Codex Wiring/Wiring Prompt NNN.md`) added at a batch gate (the user, 2026-10-29). `bash code-builders/build-and-test/how_to_reach_main.sh` says which.
- **The merge gate.** `code-builders/merge-gate/gate.sh` proves that older games replay and sweep as before. Its stages and configuration are described in [code-builders/README.md](code-builders/README.md).
- **Staging.** Stage explicit paths only. Never `git add -A` or `git add src/ASL`; never add `src/ASL/boards/` or `.claude/`. No force push.
- **Unit tests.** Run only the test methods that assert the changed behavior; the full suite waits for the gate and CI.
- **Lock files.** Restores run in locked mode. A new project reference changes the lock files of every project that depends on it, the Campaign projects included (`src/Campaign/Campaign.slnx`); regenerate and commit them with the change.
- **Out of scope.** Whatever a change leaves out or simplifies gets a row in [the backlog](<src/ASL/docs/ASL Unit Backlog.md>).
- **Tools** live under `code-builders/`, not under `src/`.
- **Files** use LF line endings and UTF-8 without a BOM.
- **Writing.** Plain language: no em-dashes, no emoticons, no marketing phrases. A hex is written in brackets, "[G4]".
- **Questions.** A question to the user carries its analysis and a proposal, never a bare question.
