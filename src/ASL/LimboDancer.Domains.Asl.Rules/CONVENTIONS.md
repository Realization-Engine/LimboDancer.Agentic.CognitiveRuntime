# Conventions of the Rules project

**Status:** Standing. Section 1 holds for every change to this project. Section 2, from the C9.3 claim (2026-10-29), says how a claim of the [Rules-first plan](<../docs/Plans/ASL Rules-First Four-Track Plan.md>) builds its calculator, whether the rule is new or already built: a claim on a built rule is its audit. Section 3, from pass 32 (the Rules migration; the redesign plan's section 19, decision 7, and section 22.2), holds for a change that moves code and changes no result; the pass 32 design, `docs/Passes/ASL Unit Backlog Pass 32 Design.md`, gives its reasons.

## 1. Every change

1. **Every ASL rule is a calculator here.** It takes facts and returns a verdict. Play reads the state and the map, hands the facts over, and writes the events; the Units projector asks the same calculators and applies the answer. Neither decides a rule of its own, and neither do ASL.Turns or the Studio's pages.
2. **One rule, one calculator.** A rule is decided in one place. A second place that decides it is a fault, whether it is in this project or outside it.
3. **This project references Abstractions only.** Never Units, Maps, or Play. Units and Play reference this project.
4. **Facts are plain.** Ints, bools, strings, and this project's own records. A three-valued fact is a `bool?`, and an unknown number an `int?`. A Location, a unit, a hexside, a facing is the string or the int the caller gives; a refusal text uses it as it stands. No type of Units or Maps crosses into this project.
5. **A fact reader is for a search only.** A calculator whose decision is a search or a scan may take a small interface declared here, implemented in Play, that returns facts: neighbors, a step's facts, who sees a Location. No reader hands over the state or the map as a whole.
6. **The recorded fact records keep their shape.** `FireAttack`, `RallyAttempt`, `CloseCombatFacts`, `VehicleCloseCombatFacts`, `AmbushFacts`, and `OrdnanceShot` are compared as serialized text by the record verifiers. No field is added, removed, renamed, or reordered.
7. **File names** take the `ScenarioA1` prefix. Definitions and tables are in `ScenarioA1Definitions.cs`, hex geometry in `ScenarioA1Geometry.cs`, result tables in `ScenarioA1ResultTables.cs`; a subsystem's calculator, models, and costs are files of their own beside the existing calculators, which do not grow.

## 2. Building a claim's calculator

The steps a claim takes on its branch, in order (AGENTS.md, step 2). The C9.3 claim is the worked example: its design, `docs/Designs/ASL C9.3 Spotters Claim Design.md`, has the map (section 2), the rulings (section 3), and the result (section 7).

1. **Map the rule's code first.** Run `python code-builders/documents/rule_sites.py <rules> --words <words>` with the claim's rule numbers and the words the code uses for them (C9.3: `--words spotter`); many places name no rule number. Read every site it lists and put each in the design's section "What decides it today" as one of three: it **decides** the rule (a fault outside Rules, a second copy inside it), it **gathers** facts for a calculator, or it **records** a verdict already given (an event, a marker). Look in Play, the Units projector (`GameProjector*.cs`), ASL.Turns, and the Studio's pages and services: C9.3's plan named two places that decided it, and the map found about twelve, the Play page's own list of Spotter candidates among them.
2. **Where the copies differ, decide between them.** Read the rule on its PDF page, choose one reading, and write each difference as a ruling of the design (RC93.3: three checklists for who may spot became one). A choice that changes what a game allows is named as a behavior change in the design and the pull request.
3. **One section, three files.** `ScenarioA1<Name>Models.cs` (the fact and verdict records), `ScenarioA1<Name>Calculator.cs` (a `static class`), and `ScenarioA1<Name>Contract.cs` (the wiring contract, registered by its `[RuleContract]` attribute). A `Turn*` rule file of the rule is folded in and removed, and its types lose the `Turn` prefix (the plan's question 7). A rule decided inside a large shared calculator moves into the claim's own file, and the shared file keeps a call (a shared hold, AGENTS.md); a rule that only modifies another calculation stays with that calculation when a ruling says so (C9.31's +2 To Hit stays in `ScenarioA1AreaCalculator.Run`).
4. **The calculator's shape.** Small checks named for the rule's own words, each returning a `bool` (`InReach`, `Retains`, `SharesWith`); for each refusal a `...Refusal` method returning `string?`, null when allowed, its text citing the rule (`CandidateRefusal`, `KeptRefusal`); the larger verdicts as records from the models file (`SpotterTimingVerdict`). An unknown fact never counts as allowed: an unknown range is not in reach, and a contract returns not-evaluated.
5. **Every caller asks; none repeats.** Play, the projector, ASL.Turns, and the Studio's pages gather the facts and call the calculator. A page that filters a list asks the same `...Refusal` the command will (C9.3: the Play page's Spotter list calls `CandidateRefusal`). Writing an event or a marker after a verdict is recording, not deciding, and stays where it is.
6. **A behavior change the rulebook requires is made; older games keep their record.** A claim may change a verdict where the rulebook says so (C9.3 stopped accepting a berserk, captured, or in-Melee Spotter). A game recorded before the change replays as it was recorded: a version on the recorded fact (C9.3's `SpotterUseVersion`) or a legacy reading keeps the old answer for old records. The merge gate shows every replay or sweep difference, and each is named as an intended change; a claim that changes none says so (`CODE_MOVE=1` in its gate configuration).
7. **Tests** are named for the calculator and the concern (`ScenarioA1SpotterTimingTests`, `ScenarioA1SpotterRetentionTests`), assert the rule's boundaries, refusals, and hidden-information cases, and run by method. A removed or renamed rule type is removed from the boundary tests' lists (`TurnRuleBoundaryTests`).
8. **Map again at the end.** Run `rule_sites.py` once more: every site outside Rules it still lists must gather or record, and the design's as-built section says so. The inventory's "Rules calculator" cell names the calculator and its methods.

## 3. Moving code without changing a result (pass 32)

1. **The order of checks is behavior.** A calculator returns the first refusal its checks give, in the order the member had them before it moved. Every refusal text is kept to the character.
2. **Two copies of a rule that differ stay two functions** while code only moves, each named for where it is used. The claim that takes the rule decides between them (section 2, step 2); the pass 32 design's section 12 lists the copies it left.
3. **A move changes no result.** The proofs: the recorded and live games replay to the same states and diagnostics, the planner answers the same requests the same way, and every refusal text and roll key is unchanged. A public name that tests or the Studio call stays where it was as a one-line forward.
