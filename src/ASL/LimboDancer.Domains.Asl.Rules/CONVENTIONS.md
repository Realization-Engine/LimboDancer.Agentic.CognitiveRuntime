# Conventions of the Rules project

**Status:** Standing. Section 1 holds for every change to this project. Section 2, from the C9.3 claim (2026-10-29), says how a claim of the [Rules-first plan](<../docs/Plans/ASL Rules-First Four-Track Plan.md>) builds its calculator, whether the rule is new or already built: a claim on a built rule is its audit. Section 3, from pass 32 (the Rules migration; the redesign plan's section 19, decision 7, and section 22.2), holds for a change that moves code and changes no result; the pass 32 design, `docs/Passes/ASL Unit Backlog Pass 32 Design.md`, gives its reasons.

## 1. Every change

1. **Every ASL rule is a calculator here.** It takes facts and returns a verdict. Play reads the state and the map, hands the facts over, and writes the events; the Units projector asks the same calculators and applies the answer. Neither decides a rule of its own, and neither do ASL.Turns or the Studio's pages.
2. **One rule, one calculator.** A rule is decided in one place. A second place that decides it is a fault: inside this project a claim removes it (section 2), outside it track 3 does.
3. **This project references Abstractions only.** Never Units, Maps, or Play. Units and Play reference this project.
4. **Facts are plain.** Ints, bools, strings, and this project's own records. A three-valued fact is a `bool?`, and an unknown number an `int?`. A Location, a unit, a hexside, a facing is the string or the int the caller gives; a refusal text uses it as it stands. No type of Units or Maps crosses into this project.
5. **A fact reader is for a search only.** A calculator whose decision is a search or a scan may take a small interface declared here, implemented in Play, that returns facts: neighbors, a step's facts, who sees a Location. No reader hands over the state or the map as a whole.
6. **The recorded fact records keep their shape.** `FireAttack`, `RallyAttempt`, `CloseCombatFacts`, `VehicleCloseCombatFacts`, `AmbushFacts`, and `OrdnanceShot` are compared as serialized text by the record verifiers. No field is removed, renamed, or reordered; a new field is a nullable property omitted from the JSON when null, and null is the reading before it, so a record written before the field serializes as it did (the user, 2026-10-30).
7. **File names** take the `ScenarioA1` prefix. Definitions and tables are in `ScenarioA1Definitions.cs`, hex geometry in `ScenarioA1Geometry.cs`, result tables in `ScenarioA1ResultTables.cs`; a subsystem's calculator, models, and costs are files of their own beside the existing calculators, which do not grow.

## 2. Building a claim's calculator

**A claim builds the Rules library, not its callers** (the user, 2026-10-29: the Rules library is built rapidly, with no dependency but its unit tests, and with minimal impact on the rest of the code; the board finding and the minigames have their UI). A claim changes the Rules project, its tests, its minigame bundle under `src/ASL/units/minigames`, and the Rule Workbench where the bundle needs it, and nothing else: Play, the Units projector and `State/`, ASL.Turns, Maps, and the Studio's other pages are track 3's, which rewires each caller to the calculator a claim built (the plan's sections 3 and 9). `claim_check.py` warns when a claim's branch changes a file outside that scope. A claim that keeps to it changes no recorded game's replay.

The steps, in order (AGENTS.md, step 2). The C9.3 claim is the example of the rule's content: its design, `docs/Designs/ASL C9.3 Spotters Claim Design.md`, has the map (section 2) and the rulings (section 3). It was made before this rule and also rewired its callers, as a claim no longer does.

1. **Map the rule's code first.** Run `python code-builders/documents/rule_sites.py <rules> --words <words>` with the claim's rule numbers and the words the code uses for them (C9.3: `--words spotter`); many places name no rule number. Read every site and put each in the design's section "What decides it today" as one of three: it **decides** the rule, it **gathers** facts for a calculator, or it **records** a verdict already given (an event, a marker). C9.3's plan named two places that decided it; the map found about twelve, in Rules, Play, the projector, ASL.Turns, and the Play page's own list of Spotter candidates. Inside Rules, the copies are the claim's to merge. Outside it, each site that decides the rule is a track 3 task: the claim lists it, with the calculator method that replaces it, in its wiring row (the inventory's section 7, the plan's section 9.1), and changes nothing there.
2. **Where the copies differ, decide between them.** Read the rule on its PDF page, choose one reading, and write each difference as a ruling of the design (RC93.3: three checklists for who may spot became one).
3. **One section, three files.** `ScenarioA1<Name>Models.cs` (the fact and verdict records), `ScenarioA1<Name>Calculator.cs` (a `static class`), and `ScenarioA1<Name>Contract.cs` (the wiring contract, registered by its `[RuleContract]` attribute). A rule decided inside a large shared calculator gets its own file; a rule that only modifies another calculation stays with that calculation when a ruling says so (C9.31's +2 To Hit stays in `ScenarioA1AreaCalculator.Run`).
4. **The calculator's shape.** Small checks named for the rule's own words, each returning a `bool` (`InReach`, `Retains`, `SharesWith`); for each refusal a `...Refusal` method returning `string?`, null when allowed, its text citing the rule (`CandidateRefusal`, `KeptRefusal`); the larger verdicts as records from the models file (`SpotterTimingVerdict`). An unknown fact never counts as allowed: an unknown range is not in reach, and a contract returns not-evaluated.
5. **The old members keep their callers and their answers.** An existing public member of Rules that callers outside it use (a `Turn*` rule, a check inside the ordnance calculator) is not removed or renamed by a claim. Where its answer agrees with the new calculator in every case, its body becomes a one-line call into the calculator. Where the claim's reading differs (C9.3 stopped accepting a berserk, captured, or in-Melee Spotter), the old member keeps its answer, and its summary names the calculator method that replaces it and the difference; track 3 moves its callers, names the behavior change, and keeps older recorded games on their recorded reading (as C9.3's `SpotterUseVersion` does), and then the old member is removed. So a claim's gate shows no replay or sweep difference.
6. **Tests** are named for the calculator and the concern (`ScenarioA1SpotterTimingTests`, `ScenarioA1SpotterRetentionTests`), assert the rule's boundaries, refusals, and hidden-information cases, and run by method. They test the new calculator; an old member's own tests stay as they are.
7. **Record the result.** The inventory's "Rules calculator" cell names the calculator and its methods. The claim's wiring row `W-<claim>` (the inventory's section 7) lists the sites outside Rules that track 3 must move, the old members it must remove, and the behavior changes it will bring. The design's as-built section lists each old member that forwards and each that still differs.

## 3. Moving code without changing a result (pass 32)

1. **The order of checks is behavior.** A calculator returns the first refusal its checks give, in the order the member had them before it moved. Every refusal text is kept to the character.
2. **Two copies of a rule that differ stay two functions** while code only moves, each named for where it is used. The claim that takes the rule decides between them (section 2, steps 2 and 5); the pass 32 design's section 12 lists the copies it left.
3. **A move changes no result.** The proofs: the recorded and live games replay to the same states and diagnostics, the planner answers the same requests the same way, and every refusal text and roll key is unchanged. A public name that tests or the Studio call stays where it was as a one-line forward.
